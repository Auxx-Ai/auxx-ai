# App Runtime Loading — How the Host Renders an App (v1)

Date: 2026-06-12 (paths updated 2026-06-17 for the `apps/web` reorg)
Status: Reference (companion to `app-implementation-template-v3.md`)

> **`apps/web` reorg note:** the host-side code moved out of `apps/web/src/{lib,providers,components}/extensions/`
> into a single `apps/web/src/components/apps/` tree — `host/` (wrapper + data handlers), `runtime/`
> (`message-client.ts`, app store, reconciler), and `providers/` (`AppsProvider`, formerly
> `ExtensionsProvider`). The `apps/api` and `packages/sdk` paths below are **unchanged**. The word
> "extension" still appears in prose as the concept name; only the file paths moved.

The v3 template documents the **authoring** contract — how an author writes an app in the
`auxxai-apps` repo and what a build produces (a content-addressed `clientBundleSha`). This doc
picks up where that ends: how a built bundle actually gets **loaded and rendered inside
`apps/web`**, and the role `apps/api` plays as the runtime host.

The template treats the platform as a black box. This is the inside of that box.

---

## 1. The Big Picture

```
apps/web (React)                 apps/api (Hono origin)              S3
─────────────────                ──────────────────────             ──────────
AppsProvider
  │ tRPC apps.listInstalled
  │   → installations[] w/ clientBundleSha
  ▼
MessageClientWrapper (one per install)
  │ new MessageClient(appId, installId, apiUrl)
  ▼
MessageClient.initialize()
  │ creates a hidden <iframe>
  │   src = {apiUrl}/app-runtime/index.html?…ctx     ─────►  serveStatic
  │   sandbox="allow-scripts allow-same-origin"               public/app-runtime/
  │                                                             ├── index.html  (static, git-tracked)
  │                                                             └── platform.{hash}.js  (built)
  │
  ▼ (inside the iframe)
  platform.{hash}.js boots, reads URL params,
  then fetches the APP bundle:
     {apiUrl}/bundles/{appId}/client/{sha}.js      ─────►  bundle-assets route
                                                            └── streams from S3  ──►  GetObject
  │
  ▼
  app bundle runs → registers surfaces/render trees
  │ postMessage  ◄──────────────────────────────────►  parent window
  ▼
data handlers in apps/web (Surfaces/Render/Dialog/Trigger/Assets/Record)
turn those messages into rendered React UI
```

Two distinct artifacts, two distinct serving paths:

| Artifact | What it is | Served by | Shared? |
|----------|-----------|-----------|---------|
| **Platform runtime** (`index.html` + `platform.{hash}.js`) | The host shell every app runs inside | `apps/api` `serveStatic` from `public/app-runtime/` | **One copy for all apps** |
| **App bundle** (`{sha}.js`) | A single app's compiled client code | `apps/api` `bundle-assets` route, streamed from the **private** S3 bucket | Per app, per build |

## 2. How `index.html` Gets Created

This is the part that surprises people: **`index.html` is not generated by a build — it's a static,
hand-authored file committed to the repo** at `apps/api/public/app-runtime/index.html`
(`git ls-files` confirms it's tracked; the `platform.*.js` next to it is not).

It's a ~80-line shell: a `#auxx-root` div, a "Loading extension…" placeholder, some inline CSS, and
one script tag:

```html
<script src="/api/v1/app-runtime/platform.3ec297e6.js"></script>
```

The **only** thing the build touches is that hash. The build pipeline:

1. **`apps/api/build-platform-runtime.ts`** (run via `pnpm --filter @auxx/api build:platform-runtime`)
   calls `buildPlatformRuntime()` from the SDK, pointing it at `apps/api/public/app-runtime/`.

2. **`packages/sdk/src/build/platform-runtime/build.ts`** esbuilds `packages/sdk/src/runtime/index.ts`
   → a single IIFE browser bundle, content-hashed (sha1, first 8 chars), emitted as
   `platform.{hash}.js` (+ sourcemap). Old `platform.*.js` files are cleaned first. Returns the hash.

3. Back in `build-platform-runtime.ts`, it reads the **existing committed `index.html`** and
   regex-replaces the `platform.{hash}.js` reference in the `<script src>` with the new hash, then
   writes it back.

So:
- **`index.html`** = static template, edited by hand, committed. Rebuilt only in the sense that its
  one script-hash line is rewritten.
- **`platform.{hash}.js`** = the actual runtime (`packages/sdk/src/runtime/` — the reconciler,
  event bus, surfaces host, server-function bridge), built fresh, content-addressed, **not committed**.

> This is why a change to `packages/sdk/src/runtime/*` requires re-running
> `build:platform-runtime` — same constraint noted in memory for SDK runtime changes
> (platform bundle, not app bundles).

## 3. How It's Served

### Platform runtime — `apps/api/src/routes/app-runtime.ts`

A Hono route mounted at `/api/v1/app-runtime`, using `@hono/node-server`'s `serveStatic` against
`./public/app-runtime`. It strips the `/api/v1/app-runtime` prefix and serves the file off disk.

**It sets no `Cache-Control` headers.** `serveStatic` does emit an `ETag`/304-on-revalidate, but
there is no `max-age`, no `immutable`, no `s-maxage`. Every iframe boot makes a conditional request
back to the API origin for both `index.html` and `platform.{hash}.js`.

### App bundle — `apps/api/src/routes/bundle-assets.ts`

A Hono route at `/api/v1/bundles/:appId/:bundleType/:sha.js`. It:
1. Looks up the `AppBundle` row (verifies it exists and `uploadedAt` is set),
2. Streams the object from the **private** S3 bucket — `auxx-private`, key
   `apps/{appId}/bundles/{client|server}/{sha}.js` (`getBundleS3Key`, `getS3BucketName()` →
   `S3_PRIVATE_BUCKET`),
3. Sets `Cache-Control: public, max-age=31536000, immutable` (correct — content-addressed).

The file's own header comments spell out an intended evolution:

```
// Phase 1: Streams S3 content through the API.
// Phase 2: Returns 302 to a stable CloudFront URL.
```

We are on **Phase 1**: every app-bundle fetch is proxied byte-for-byte through the API process
(`s3Client.send(GetObjectCommand)` → `transformToWebStream()`), even though the content is immutable
and already in S3.

> Note: the "Phase 2 → CloudFront" comment is stale relative to how we actually run. We don't use
> CloudFront in production (see §6). Both bundle types currently live in the **private** bucket —
> the *server* bundle must stay private (it runs server-side), but the *client* bundle is shipped to
> browsers anyway, so privacy isn't the gate for it.

## 4. The Two-Stage Load (why an iframe at all)

`apps/web/src/components/apps/runtime/message-client.ts` runs the app in a **cross-origin sandboxed iframe**
rather than in the host page. The iframe `src` is `{apiOrigin}/app-runtime/index.html?{ctx params}`
with `sandbox="allow-scripts allow-same-origin"`, and context (orgId, handle, userId, apiUrl,
isDevelopment, …) is passed as URL query params.

Load is explicitly two-staged:
- **Stage 1** — the iframe HTML (`index.html` + `platform.{hash}.js`) loads. `MessageClient`
  resolves on `iframe.onload` (with a cached-iframe fallback that synthesizes `onload`).
- **Stage 2** — inside the iframe, the platform runtime fetches the **app** bundle URL passed by
  `MessageClientWrapper` (`{apiUrl}/bundles/{appId}/client/{clientBundleSha}.js`) and signals ready.
  Only then does `MessageClientWrapper` call `store.setMessageClient(...)`, wiring the app into the
  `AppStore`.

All subsequent communication is `postMessage` over that iframe, targeted to the API origin. The data
handlers in `apps/web/src/components/apps/host/data-handlers/` (`Surfaces`, `Render`, `Dialog`,
`Trigger`, `Assets`, `Record`) translate those messages into rendered React.

**Why cross-origin + sandboxed:** apps run untrusted third-party code. Hosting them on the API origin
(not the web origin) with a `sandbox` attribute isolates them from the host's cookies/DOM/session;
`postMessage` is the only channel across the boundary.

> Origin reality: `apps/api` runs on **Railway**, fronted by **Cloudflare** (proxied; origin shows
> `x-railway-edge`). So `{apiUrl}` = `https://api.auxx.ai` resolves Cloudflare → Railway. The iframe
> HTML, the runtime JS, and the app-bundle stream all terminate at that one Railway API process.

## 6. The CDN Question

Short answer: **these immutable assets should be on our CDN, and today none of them are.**
Everything an app needs to boot — iframe HTML, platform runtime JS, app bundle — is served by
hitting the Railway API process directly, on the hot path of every page that mounts apps.

### What our CDN actually is

We do **not** use CloudFront in production. The `infra/storage.ts` CloudFront distribution
(`sst.aws.Cdn('PublicCdn')`, `cdn.auxx.ai`) is part of the **SST/AWS dev-stage** definition and is
not the production serving path — same pattern as AWS Lambda being superseded by Railway.

The real production CDN is a **Cloudflare Worker fronting the `auxx-public` S3 bucket**, exposed at
**`cdn.auxx.ai`**. That's where public, cacheable assets belong. The worker is a thin pass-through to
`auxx-public` in `us-west-1`:

```js
export default {
  async fetch(request) {
    const url = new URL(request.url)
    const origin = `https://auxx-public.s3.us-west-1.amazonaws.com${url.pathname}`

    // Edge-cache everything for a day; S3 already sets correct Content-Type
    const res = await fetch(origin, {
      cf: { cacheEverything: true, cacheTtl: 86400 },
    })

    const headers = new Headers(res.headers)
    headers.set('Cache-Control', 'public, max-age=86400')
    return new Response(res.body, { status: res.status, headers })
  },
}
```

**Two behaviors to note before routing runtime assets through it:**

1. It **hardcodes `Cache-Control: public, max-age=86400`** (1 day) on *every* response, overwriting
   whatever the S3 object sets. So content-addressed assets that want `immutable, max-age=31536000`
   would be capped at a 1-day browser TTL as the worker stands today.
2. The Cloudflare **edge** TTL is also fixed at `cacheTtl: 86400`, path-independent.

Neither is fatal (1-day caching is still a big win over streaming through Railway on every boot), but
a proper migration would make the worker **path-aware** — `immutable`/1-year for `platform.{hash}.js`
and the content-hashed `{sha}.js` bundles, short TTL for `index.html` (the mutable pointer).

### What's wrong today

1. **App bundles are proxied through the Railway API (Phase 1).** Immutable, content-addressed,
   already in S3 — the textbook edge-cache case — yet every fetch streams through the API process
   via `GetObjectCommand`. And they sit in the **private** bucket, so they can't be fronted by
   `cdn.auxx.ai` as-is.

2. **The platform runtime sets no cache headers at all.** `index.html` *should* be short-cache /
   revalidate (it's the mutable pointer to the current hash), but `platform.{hash}.js` is
   content-hashed and should be `immutable, max-age=31536000` exactly like bundle-assets — it gets
   neither, so it's re-fetched from the Railway origin on every iframe boot.

### A reasonable target state (using what we already run)

- **Client app bundles** → publish to the **`auxx-public`** bucket (they ship to browsers anyway;
  privacy was never the gate for the *client* bundle) and serve via **`cdn.auxx.ai`**. The
  `bundle-assets` route either 302-redirects to the CDN URL or is retired for the client type.
  **Server bundles stay in `auxx-private`** — they must never be publicly fetchable.
- **`platform.{hash}.js`** → push to `auxx-public` at `build:platform-runtime` time, serve via
  `cdn.auxx.ai`. It's identical for every app, so this is the highest-leverage cache win — but to get
  true `immutable` caching the worker needs the path-aware change noted above (it currently caps
  everything at 1 day).
- **`index.html`** → keep on the API (or also on the CDN) with a short TTL + revalidate, since it's
  the one mutable file. Point its `<script src>` at the CDN-hosted `platform.{hash}.js`.

This is a follow-up, not part of the authoring template — but it's the obvious next step for the
runtime-loading path, and it should target the **Cloudflare Worker + `auxx-public`** CDN, not the
dormant SST CloudFront definition. Flagging it here so the gap is documented rather than
rediscovered.
